# 从生成环境到专用推理引擎

InferenceForge 的目标是让模型、硬件、请求特征决定引擎实现。用户获得一个能启动、能接入应用、能复现性能的产物；研究者可以检查它是怎样被构造出来的。

## 从 Strata 吸收什么

[Strata](https://github.com/Niko1221/Strata/blob/main/README.zh-CN.md) 展示了清楚的产品形态：用户选择模型，运行适合自己机器的引擎。其 [技术说明](https://github.com/Niko1221/Strata/blob/main/docs/DETAILS.md) 明确区分 Qwen 与 DeepSeek 引擎，参数与测量也绑定模型、硬件、量化和上下文。这比一个覆盖所有模型的模糊“更快”承诺更有说服力。

其 [实现说明](https://github.com/Niko1221/Strata/blob/main/docs/HOW_IT_WORKS.md) 包括针对模型结构的 GPU/CPU/SSD 分工、专家缓存、投机解码等。应吸收的是识别瓶颈并跨层协同的做法。具体技术是否适合 Qwen3-8B，要由实际负载决定；dense 8B 不能套用 MoE 专家卸载收益。这里引用的是上游说明，我们尚未独立复现 Strata 的速度。

## 保持简单的仓库结构

| 位置 | 内容 |
| --- | --- |
| `targets/` | 模型 revision、硬件、负载、精度、约束；由实际准备和评测程序消费 |
| `forge/` | 构造与执行反馈工具，以及当前可运行种子 |
| `engines/` | 已生成引擎的目录与运行入口；每个引擎明确支持范围 |
| `examples/generated/` | 当前已测的生成源码，保留历史路径 |
| `scripts/` | 权重准备与运行辅助工具 |
| `results/` | 可公开的实测记录；源码身份、设备、负载、错误和统计 |

目前不增加平台插件系统、统一中间表示或远程管理平台。出现第二个真实需要不同实现的目标时，再提炼共享能力。构造器不会出现在逐 token 的执行路径。

## 首个 8B 目标

固定 `Qwen/Qwen3-8B`、BF16、单 A40、TP=1；优先对话延迟与批量吞吐两类开发负载。先验证完整模型前向、Q/K norm、RoPE、KV 续写与并发状态，再优化执行和调度。禁止用 Qwen2.5-0.5B 的提速作为 8B 结果，也不将调参 vLLM 包装成自生成引擎。

执行反馈要能帮助下一次修改：给出首个数值偏差的位置、触发它的请求序列，以及 prefill、decode、队列等待和显存的实际开销。昂贵的全量评测放在候选通过快速检查之后。优化是否有效，最终仍由固定外部负载判定。

## 论文的两个比较

1. **构造能力**：在明确起点、实际生成模型和预算下，比较 InferenceForge、VibeServe、MetaInfer 产出可运行且正确引擎的比例、时间、资源费用和最终性能。原生流程与任务适配版本分别标注。不同生成模型的结果不能单独归因于环境设计。
2. **运行性能**：固定模型文件、精度、GPU、token 输入、输出长度与缓存条件，对比生成引擎、vLLM、SGLang。保留成熟基线的正常优化能力，给它们同等调参预算；同时测吞吐、首 token 延迟、逐 token 延迟、尾延迟与失败。

核心可检验假设是：任务相关的执行反馈能用相同构造预算得到更快且正确的引擎。用相同生成模型、相同起点、相同预算下的稀疏反馈对照来检验。最终留出负载在开发结束前保持封存；开发阶段结果不升级为泛化结论。

## 存储与推理消费者共同生成

主要参考 [BespokeOLAP](https://github.com/DataManagementLab/BespokeOLAP/tree/e5c5acd373a802d3f13f9be04387d79ca35a072a) 为负载共同设计物理表示与执行代码的方式。首个8B实验已经生成了配套的主机KV存储和会话消费者，并在相同预算下交叉组合旧/新组件。

目前结果表明：减少传输载荷不一定改善完整请求。新组件可以保持状态并减少重复写回，但当前多会话中位收益只有约0.815%，证据不足。下一步需要结合实际执行瓶颈验证布局与消费者的进一步特化，同时保留成熟框架和独立生成对照。详见[可复现实验](../experiments/qwen3_8b/README.md)。

## 一个引擎何时能发布

发布包包含生成源码、依赖版本、启动命令、适用目标、独立正确性记录和原始性能记录。状态依次为准备中、已构建、已验收、已测量。新模型仅有配置文件时仍是准备中；一次命令退出成功不能替代其余证据。
